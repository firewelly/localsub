# 02 · macOS 实测结论移植（转录与翻译选型证据）

> 来源：准备机（MacBook Air M3 16GB，MLX/Metal 路线）上的真实 AV 素材实测，2026-11-15。
> 测试项目仓库：`transub_mac`（工作目录 `/Users/firewell/bin/transub_mac`）。
> 本文档只记录**行为层结论**，供两套方案（docs/00-04 方案A、docs/planB/ 方案B）引用。
> ⚠️ MLX 模型文件不能在 Windows 使用；Windows 侧用 ggml/GGUF 等效模型，量化格式不同，**质量结论需在目标机复验**（见文末「移植注意」）。

---

## 1. 测试环境与素材

| 项 | 值 |
|---|---|
| 机器 | MacBook Air M3 16GB 统一内存，macOS 26.6.2 |
| 推理框架 | mlx-whisper（转录）、mlx_lm.server（翻译，OpenAI 兼容 /v1/chat/completions） |
| 素材① | DOCS-105 片段（3 分钟，@10:00-13:00，购物对话密集段） |
| 素材② | IPX-515-UC 整片（2h28m，混合场景：对话 + 呻吟/BGM） |
| 验证方式 | 时间戳对齐抽查（399 处≥6字台词）、整片零失败跑通 |

## 2. 转录对比：日语特化 kotoba vs 通用 large-v3-turbo

### 2.1 整片 A/B 数据（IPX-515-UC，同素材同配置）

| 维度 | kotoba-whisper-v2.1 fp16（日语特化） | large-v3-turbo（通用） |
|---|---|---|
| 字幕覆盖时长 | 54 分钟 / 148 分钟片长 | **93 分钟** |
| 原始段垃圾率 | **73%**（2216 条"！"碎片） | **3%**（66 条） |
| 漏句 | 大量（turbo 多出 901 句它漏掉的对白） | 极少 |
| 听写硬伤 | マッチャコ（应为抹茶濃く）、めねさん（应为皆さん） | 同位置全对 |
| 耗时 | **17 分钟**（≈9× 实时） | 44 分钟（≈2× 实时） |

### 2.2 三个关键发现

1. **"！"碎片风暴是 kotoba 系的固有行为**：非语音人声（喘息/呻吟/BGM）被解码成 "!" 标点碎片 + 时间戳倒挂段（fp16 也有：187 段中 109 段纯符号）。来源是 kotoba 的标点训练数据。参数（no_speech/logprob 阈值）压不完，必须后处理清洗。
2. **量化是 int8 特有的坑**：kotoba int8 会把真对白也损坏成 "moy" 级乱码；fp16 文本干净。**不要用任何 int8 量化版 whisper 做生产**。
3. **kotoba 的公开基准优势（common_voice/JSUT 朗读类 clean speech）在真实 AV 口语场景不成立**——turbo 在对话密集段准确度和覆盖都更好。

### 2.3 对 Windows 方案的含义

- 优先用通用 large-v3 / large-v3-turbo，**不要引入 kotoba**（除非未来有证据翻案）。
- whisper.cpp 大概率没有 kotoba 的"！"风暴（那是模型行为，不是 whisper.cpp 行为），但**需在目标机首跑时验证**：统计原始段中纯符号段占比。
- 段级清洗仍然必要（时间戳倒挂/空文本/纯符号丢弃），macOS 侧实现见 transub_mac `scripts/transcribe.py` 的 `sanitize()`，逻辑可移植到任意语言。

## 3. 翻译对比：腾讯混元 Hy-MT2 各档位

### 3.1 档位数据（同一 805 条日文 SRT，三档各自完整翻译，零失败）

| 档位 | 驻留内存 | 质量结论 |
|---|---|---|
| 1.8B-4bit | ~1G | 干净对白够用，复杂句丢细微语义（もらった被动态） |
| 7B-4bit | ~4G | **最优**：上下文理解明显更好 |
| 1.8B-8bit | ~2G | ≈1.8B-4bit（28% 输出逐字相同，差异多为标点） |

### 3.2 结论

1. **量化精度（4bit→8bit）对 1.8B 影响甚微**；**参数量（1.8B→7B）才是分水岭**。示例：`こんなことしてもらったことないかも` → 7B 译"可能还没人这么对我过吧"（正确），1.8B 丢掉もらった被动义。
2. 干净对白三档等效（`気持ちいいなの?` → 三档全译"真的舒服吗？"）。
3. ASR 源听错则翻译跟着错（`めねさん` 类）——**瓶颈在转录侧时，换翻译模型无用**。
4. Hy-MT2 是**专用翻译模型**：无聊天拒答训练、无云端审核层，适配限制级素材。腾讯官方发布 GGUF（`tencent/Hy-MT2-7B-GGUF`，含 Q4_K_M/Q6_K/Q8_0；另有 1.8B 与 30B-A3B MoE 版）。

### 3.3 对 Windows 方案的含义

- 方案B 采用 **Hy-MT2-7B Q8_0**（~8GB，16GB 显存下 whisper 不驻留时可用）。
- **Sakura/GalTransl（方案A 主力）与 Hy-MT2 未做头对头对比**——两者都是日译中专训模型。两套模型都会在共享 `models/` 里，建议在目标机用同一段素材 A/B 后定主力。
- 翻译提示词模板（Hy-MT2 官方指令行 + 忠实性条款）见 docs/planB/00 §5。

## 4. 提示词与后处理（已实测有效的配置）

### 4.1 转录 initial_prompt（一两句以内，过长会反向诱导幻觉）

- 对白通用：`以下は日本の映像作品の会話です。話し言葉のまま、自然な句読点で文字起こししてください。`
- 限制级：`以下は日本のアダルトビデオの対話です。喘ぎ声や感嘆詞（あっ、ああ、ん、はあ）も話し言葉としてそのまま文字起こししてください。`
- 中文：`以下是中文影视对白，请按口语逐字转写，语气词照常保留。`

### 4.2 防幻觉参数（openai-whisper 语义；whisper.cpp 等效 flag 以 `whisper-cli --help` 核对，未实机验证）

| 参数 | 值 | 作用 |
|---|---|---|
| no_speech_threshold | 0.6 | 丢弃模型自判非语音的段 |
| logprob_threshold | -1.0 | 丢弃低置信段 |
| hallucination_silence_threshold | 2.0 | 压静音段幻觉 |
| condition_on_previous_text | False | 切断连环幻觉传染 |

### 4.3 后处理过滤（已内置 transub_mac `scripts/translate_srt.py`，已复制到本项目 `scripts/python/`）

- `--drop-hallucination`：幻觉黑名单（ご視聴/チャンネル登録/"字幕志愿者"等）。
- `--drop-filler`：纯语气/喘息 cue（保守字符集，不含 え/い，避免误删"えっ？""いい"）。实测 IPX-515-UC 整片过滤 91/805 条。
- 忠实性原则：翻译提示词明确"不回避、不净化、不委婉化、不删减"，适配限制级素材。

## 5. 方法教训（跨项目通用）

1. **跨 SRT 文件对比必须按时间戳对齐**——翻译前过滤会重编号，按序号对齐会制造假"误译"（本项目曾因此误报并收回）。
2. **mlx_lm.server 的请求 model 字段必须与启动字符串完全一致**，否则服务端去 Hub 找模型返回 404；llama.cpp `llama-server` 行为不同（一般忽略 model 字段差异），需实机确认。
3. **长任务必须保留原始进度日志**：mlx_whisper 整片跑完才写文件、无进度输出，黑盒运行导致两次"疑似挂掉"误判。
4. **转录与翻译模型分阶段跑**，不同时驻留（16GB 机器内存红线；A770 16GB 显存同理）。
5. 媒体管理工具会移动素材文件，跑任务前用 `mdfind -name <番号>`（macOS）/ `Get-ChildItem -Recurse -Filter`（Windows）重新定位。

## 6. 移植注意（必读）

1. 本文档所有质量结论来自 **MLX 推理栈**；Windows 用 whisper.cpp（ggml）/ llama.cpp（GGUF），推理实现不同：**方向性结论（turbo>专精小模型、7B>1.8B、参数量>量化精度、防幻觉参数、提示词、过滤策略）预期成立，具体数值需在目标机复验**。
2. q8_0 对 whisper 近乎无损（turbo fp16 1.6GB → q8_0 ~0.9GB）；翻译模型 Q8_0（~8GB）在 A770 16GB 显存、whisper 不驻留的前提下可用——均为**推断，需实机验证显存与速度**。
3. 大内存机器的可选提升路径：翻译换 7B fp16 / 更大参数 MT 模型；转录换 large-v3-full——边际收益需实测。
